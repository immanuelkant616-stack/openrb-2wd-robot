# 오류 해결 기록

[README로 돌아가기](../README.md)

실습 중 발생한 문제를 증상·판단 근거·대응으로 나누어 기록했다. 처음 추정했던 원인을 확정된 사실로 바꾸어 적지 않았다.

## 1. 보드·포트 인식 및 업로드

- **증상:** 포트가 보이지 않거나 `no upload port provided`, `No device found on ttyACM0` 등의 메시지가 나타났다.
- **점검:** USB 데이터 통신 가능 여부, 보드·포트 선택, 리셋 후 연결 상태를 확인했다.
- **대응:** 데이터 케이블 교체, 포트 재선택, 리셋·IDE 재시작 등을 거쳐 Blink 업로드와 모터 코드 업로드에 성공했다.
- **범위:** 충전 전용 케이블 사용은 초기 추정 원인 중 하나다. 각 조치가 어떤 오류를 단독으로 해결했는지에 대한 완전한 로그는 없다.

다시 발생하면 현재 보드명·포트명·업로드 전체 메시지를 먼저 기록한다. `/dev/ttyACM0`의 숫자가 항상 같다고 가정하지 않는다.

## 2. `reference to 'ID' is ambiguous`

컴파일러가 사용자 코드의 `ID`와 라이브러리의 `ControlTableItem::ID`를 구분하지 못했다.

문제가 있었던 이름의 예:

```cpp
const uint8_t ID = 1;
```

모터 주소 변수 이름을 구체적으로 바꾸어 해결했다.

```cpp
const uint8_t MOTOR_ID = 1;
```

두 모터 코드에서는 `MOTOR1_ID`, `MOTOR2_ID`를 사용한다. 변수 선언뿐 아니라 사용하는 곳도 함께 바꾸었다. 라이브러리의 제어 항목은 `ControlTableItem::...` 형태로 지정한다.

## 3. 새 명령을 보내도 이전 프로그램의 동작이 실행됨

ID 설정을 하려는데 `READY: type s...`가 반복되어 `s`를 보냈고, 모터가 잠깐 움직였다. 이 문구는 이전 한 모터 구동 코드의 안내였다.

IDE에서 새 파일을 여는 것만으로 보드의 프로그램은 바뀌지 않는다. 업로드 후 안내 문구로 현재 프로그램을 확인하도록 절차를 바꾸었다. `✓`는 컴파일 검증이고, `→`가 보드 업로드다.

| 시리얼 안내 문구 | 의미 |
| --- | --- |
| `READY: type s...` | 이전 한 모터 구동 프로그램. 여기서 `s`는 시작 명령이었음 |
| `ID SETUP: second motor ONLY...` | 이 저장소에 포함된 단일 모터용 ID 설정 도구 |
| `ID SETUP \| p: inspect \| t: first 1->10...` | 당시 검토한 임시 ID 변경 도구. 이번 저장소의 실행 대상에는 포함하지 않음 |
| `READY \| p: check IDs \| 1: motor 1...` | 현재 두 모터 위치 이동 시험 프로그램 |

프로그램마다 같은 문자의 의미가 다를 수 있다. 시리얼 모니터 속도는 115200 baud로 맞춘다.

## 4. 모터 ID와 코드 변수명의 혼동

`MOTOR_ID`는 코드에서 사용하는 이름이고, `1`은 그 이름에 저장한 숫자다. 모터 내부의 통신 주소를 변경하려면 별도의 `setID()` 명령이 필요하다.

두 모터를 연결한 상태에서 최종적으로 다음 응답을 확인했다.

```text
FOUND: ID=1 Model=1200
FOUND: ID=2 Model=1200
```

이 결과를 확인한 뒤에는 ID를 다시 바꾸지 않고 두 모터 구동 코드로 전환했다. 원문은 [검색 로그](../logs/id-scan-observed.txt)에 보관했다. 실제 ID 변경 명령의 전체 실행 순서는 기록이 부족하므로 재구성해 주장하지 않는다.

## 5. 커넥터가 잘 빠지지 않음

### 문제와 판단

OpenRB-150에 연결한 첫 번째 모터의 커넥터가 뻑뻑해 분리하기 어려웠다. 두 번째 모터를 한 개만 연결해 ID를 설정하라는 초기 안내대로 하려면 기존 연결을 먼저 풀어야 했다. 그러나 커넥터나 보드 단자가 손상될까 우려되어, 힘을 주어 당기는 대신 **첫 모터 케이블을 유지한 상태에서 두 번째 모터를 추가하는 방법**을 모색했다. 실제 파손이 발생했다는 뜻은 아니다.

### 해결 접근: 단자 위치 대신 ID로 구분

모터를 구분하는 기준은 보드의 단자 위치가 아니라 모터 내부의 통신 주소인 ID다. 따라서 기존 모터의 주소를 임시로 옮겨 새 모터와 주소가 겹치지 않도록 하는 절차를 대안으로 마련했다. 당시 제공된 `ids_without_unplug.ino`는 아래 순서로 구성되었다. 이 파일은 현재 저장소의 실행 코드에는 포함하지 않는다.

| 단계 | 연결 상태와 조작 | 의도한 ID 상태 |
| --- | --- | --- |
| 1 | 기존 모터만 연결된 상태에서 `t`: 기존 ID `1 → 10` | 기존 모터 10, 새 모터는 아직 연결하지 않음 |
| 2 | USB 전원을 끄고 기존 모터 케이블은 유지한 채 새 모터를 빈 DXL 단자에 추가한 뒤 전원 재연결 | 기존 모터 10, 기본 ID가 1인 새 모터 1 |
| 3 | `p`로 상태 확인 후 `n`: 새 모터 ID `1 → 2` | 기존 모터 10, 새 모터 2 |
| 4 | `r`: 기존 모터 ID `10 → 1`, 이후 `p`로 확인 | 기존 모터 1, 새 모터 2 |

이 절차는 **두 모터를 같은 ID로 연결해 놓고 검색으로 골라내는 방식이 아니다.** 첫 단계에서는 기존 모터만 연결되어 있어야 하며, 새 모터를 추가하기 전에 기존 모터의 ID가 10으로 바뀌었는지 확인해야 한다. 임시 ID 10과 목적지 ID는 비어 있어야 한다. 당시 코드는 목적지 ID의 응답 여부, 모델 번호, 토크 해제 성공 여부와 변경 후 주소 응답을 점검하도록 작성되었다.

### 실제로 확인한 결과

두 모터를 연결한 뒤 `p`로 전수 검색했을 때 다음 응답을 확인했다.

```text
Scanning IDs 0..252 at 57600 bps. Please wait...
FOUND: ID=1 Model=1200
FOUND: ID=2 Model=1200
```

이 결과를 확인한 뒤에는 ID를 더 변경하지 않고 두 모터 구동 코드로 전환했다. 이후 `b` 입력으로 두 모터가 모두 움직였고, `s`를 따로 누르지 않아도 자동으로 멈추는 것을 확인했다. [최종 ID 검색 로그](../logs/id-scan-observed.txt)는 저장소에 보관했다.

**기록 범위:** 커넥터 분리의 어려움과 손상 우려, 분리하지 않는 대안을 모색한 과정, 최종 두 ID의 응답과 구동 결과를 기록한다. 임시 ID 10을 거친 개별 변경 명령의 전체 실행 로그는 남아 있지 않다. 따라서 위 표는 당시 마련한 해결 절차를 설명하며, 모든 단계를 실제 완료했다는 증거로 제시하지 않는다. 전원이 켜진 상태에서 모터 케이블을 꽂거나 뽑았다는 뜻도 아니다.

### 배운 점

부품을 분리하기 어렵다는 물리적인 제약을 만났을 때, 무리하게 힘을 가하기보다 통신 주소를 관리하는 방법을 찾아 연결 확장을 검토했다. 또한 해결 절차를 제안한 것과 실제 장치에서 결과를 확인한 것을 구분하고, 주소 변경 전후의 응답을 기록하는 중요성을 배웠다.

현재처럼 ID 1·2가 이미 확인된 장비에서는 이 임시 변경 절차를 반복하지 않는다.
